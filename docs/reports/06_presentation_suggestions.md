# BTS 발표 제안서 (기술 외 발표 구성 포함)

## 0. 발표에서 가장 중요한 판단

이번 발표는 “기능이 많다”를 나열하면 점수가 오르지 않는다.  
오히려 아래 한 줄이 관통해야 한다.

> **감독이 선수들에게 일일이 연락하던 비효율을, 역할 기반 앱 흐름으로 줄였다.**

즉, 발표의 중심은
- 화면 수
- 코드량
- AI 화려함

이 아니라

- **현실 문제**
- **왜 이 문제를 이렇게 구조화했는가**
- **실제로 사용하면 무엇이 줄어드는가**

여기에 있어야 한다.

## 3. 발표에서 반드시 넣으면 좋은 정량 프레임

너무 많은 팀 발표가 “편해졌습니다” 에서 끝난다.  
그 표현은 약하다.  
발표에서는 형용사 대신 **비교 식**으로 말하는 편이 강하다.

## 추천 프레임 1. 커뮤니케이션 비용 비교
### 기존 방식
- 경기 1개당 감독이 선수 N명에게 개별 연락
- 응답 누락 / 재확인 / 채팅방 스크롤 비용 발생

### BTS 방식
- 기록원/관리자가 일정 1회 등록
- 선수는 앱에서 상태 표시
- 감독은 참석 가능 선수만 확인

### 말하기 좋은 문장
> 기존 방식의 비용은 `경기 수 × 선수 수 × 확인 횟수` 에 비례하지만,  
> BTS 방식은 `경기 수 × 상태 확인 횟수` 로 줄어든다.

이건 실제 수치를 아직 안 넣더라도 설득력이 있다.

---

## 추천 프레임 2. 의사결정 단계 수 비교
### 기존
1. 일정 전달
2. 개인별 확인
3. 응답 수집
4. 재확인
5. 참석 가능자 정리
6. 라인업 작성

### BTS
1. 일정 등록
2. 선수 참석 체크
3. 참석 가능자 기반 라인업 작성

### 발표용 점수
- 이해도: `10/10`
- 시각화 용이성: `10/10`

## 추천 프레임 3. 기능이 아니라 흐름으로 설명하기
아래처럼 말하는 편이 좋다.

### 좋지 않은 방식
- 로그인 기능 구현
- 일정 화면 구현
- 팀 화면 구현
- 리뷰 기능 구현

### 좋은 방식
- 기록원이 일정을 올린다.
- 선수가 참석 여부를 체크한다.
- 감독이 라인업을 짠다.
- 경기 후에는 선수 리뷰와 기록을 확인한다.

왜냐하면 BTS는 화면 모음이 아니라 **운영 프로세스 앱**이기 때문이다.

## 4. 데모 순서 추천

## 가장 좋은 라이브 데모 순서 (`10/10`)
1. **기록원** 화면에서 일정 등록/수정 화면 보여주기
2. **선수** 화면에서 참석 체크 보여주기
3. **감독** 화면에서 참석 가능한 선수 기반 라인업 구성 보여주기
4. **MyGame** 에서 저장된 라인업 확인
5. **PlayerDetail** 에서 기록 / 리뷰 / PR 카드 보여주기

이 순서가 좋은 이유:
- 문제 해결 흐름과 정확히 일치한다.
- 앞에서 만든 데이터가 뒤 화면으로 이어진다.
- “기능 나열”이 아니라 “시나리오”가 된다.

## 7. 발표에서 넣으면 좋은 협업 내용

## 7-1. 브랜치 전략이 바뀐 이유 (`9/10`)
이건 그냥 “우리는 dev 썼습니다” 로 끝내지 말고, 아래처럼 설명하는 편이 좋다.

### 말하기 좋은 구조
1. 처음에는 `main` 에서 바로 개인 브랜치 분기
2. 머지 시 충돌 해결 부담이 스크럼 마스터에게 몰림
3. 그래서 `dev` 중심으로 전략 변경
4. 개인 브랜치에 `dev` 를 먼저 반영하고 충돌 해결
5. 이후 `dev` 로 `squash and merge`

### 왜 좋은가
- Git을 처음 써봤다는 점을 숨기지 않으면서도
- 프로젝트 중간에 협업 방식을 개선했다는 점을 보여준다.

---

## 7-2. 하루 12시 5분 스크럼 (`8/10`)
이건 짧아 보여도 의미가 있다.

### 발표 포인트
- 짧지만 매일 했다.
- 기능 구현 진척과 충돌 이슈 공유에 사용했다.
- 브랜치 전략 변경 같은 실무적 의사결정이 이 흐름에서 나왔다.

즉, “형식적으로 한 회의”가 아니라  
**짧은 리듬으로 계속 정렬한 장치**로 말하는 편이 좋다.

## 11. Q&A 예상 질문과 답변 프레임

### Q1. 왜 이 프로젝트가 필요한가?
**답변 프레임:**  
감독이 선수별 참석 여부를 수동 확인하는 현실 문제를 줄이기 위해서다.  
BTS는 일정-참석-라인업을 하나의 앱 흐름으로 묶는다.

### Q2. 기술적으로 가장 어려웠던 부분은?
**답변 프레임:**  
라인업 편성 로직과 역할별 화면 분기였다.  
특히 참석 가능한 선수만 대상으로 수비와 타순을 동시에 맞추는 규칙이 필요했다.

### Q3. 왜 DB를 이렇게 설계했는가?
**답변 프레임:**  
MVP 속도를 위해 JSON 기반 구조를 택했다.  
운영 단계에서는 정규화 테이블로 확장할 수 있다.

### Q4. 현재 한계는?
**답변 프레임:**  
배포 준비, 환경변수 분리, 인증 일원화, CSV UI 연결이 남아 있다.

### Q5. 가장 자랑하고 싶은 기능은?
**답변 프레임:**  
핵심 문제 해결 관점에서는 참석 관리 → 라인업 흐름이고,  
차별화 관점에서는 리뷰/PR 카드 기능이다.

## 13. 최종 추천

### 발표 핵심축
- 문제 정의: `10/10`
- 유저 플로우: `10/10`
- 라인업 기술 설명: `10/10`
- 협업/회고: `8/10`
- AI 확장 기능: `7/10`

### 가장 좋은 발표 한 줄 구조
> **왜 필요했는가 → 어떻게 흐름을 바꿨는가 → 무엇을 구현했는가 → 어디까지 개선할 것인가**

이 순서로 가면,
- 현실 문제
- 제품 흐름
- 기술 구현
- 성찰
이 모두 들어간다.

즉, BTS 발표의 포인트는  
**“우리가 많은 기능을 만들었다”** 가 아니라  
**“우리가 한 번의 수작업 운영 문제를 하나의 앱 플로우로 바꿨다”** 에 있어야 한다.
