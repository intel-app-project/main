# BTS 기술 발표 주제 제안

## 0. 먼저 정리할 기준

기술 발표에서 좋은 주제는 아래 4개 점수가 높아야 한다.

- **문제 연결성**: `이 기술이 왜 필요한가`를 바로 설명할 수 있는가
- **코드 근거성**: 저장소에서 실제 코드로 보여줄 수 있는가
- **차별성**: 평범한 CRUD를 넘는가
- **질문 유발성**: 교수/청중이 기술적으로 물어볼 거리가 있는가

이번 프로젝트에서 그 기준으로 보면, **핵심 문제 해결 흐름**과 **규칙 기반 라인업 로직**, **AI 리뷰/PR 카드 파이프라인**, **혼합형 아키텍처**가 가장 강하다.

## 2. 발표에서 가장 좋은 메인 테마

## 메인 테마 제안
> “사회인 야구 운영의 수작업 문제를, 역할 기반 모바일 플로우와 규칙 기반 라인업 로직으로 어떻게 줄였는가”

이 문장이 좋은 이유:

- AI 기능은 뒤에 확장 기능으로 붙이기 쉽다.

점수:
- 문제-기술 연결성: `10/10`
- 발표 완성도: `9/10`

## 3. 기술 발표에서 꼭 다루면 좋은 내용

## 3-1. 역할 기반 앱 아키텍처 (`10/10`)
### 왜 좋은 주제인가
이 앱은 단순히 “여러 화면이 있다”가 아니라, 로그인 이후 역할에 따라 **탭 구조 자체가 달라진다.**

### 실제 코드 근거
- `app/App.js`
- `app/navigation/MainTabNavigator.js`
- `app/components/CommonFooter.js`
- `app/screen/loginScreen.js`

### 발표 포인트
1. 로그인 후 `Primary_Position` 으로 역할 분기
2. 감독 / 선수 / 기록원의 메뉴 구조 차이
3. 기록원은 푸터를 숨기고 일정 관리 중심으로 진입
4. 역할 기반 화면 분기가 왜 문제 해결과 연결되는지 설명

### 보여주면 좋은 코드
- `MainTabNavigator.js` 의 `isDirector`, `isManager` 분기
- `LoginScreen.js` 의 로그인 성공 후 `navigation.reset(...)`

### 예상 질문
- 왜 역할 분기를 프론트에서 먼저 처리했는가?
- 권한 검증을 프론트만으로 해도 되는가?
- 운영 단계에서 이 구조를 어떻게 강화할 것인가?

### 이 질문이 좋은 이유
이 질문이 나오면 자연스럽게 **인증/권한/백엔드 일원화**로 넘어갈 수 있다.

## 3-2. 참석 관리가 라인업 편성으로 이어지는 흐름 (`10/10`)
### 왜 좋은 주제인가
이건 BTS의 핵심 문제 해결 그 자체다.

문제:
- 감독이 매번 한 명씩 연락해야 한다.

해결:
- 선수가 먼저 참석 여부를 표시한다.
- 감독은 참석 가능한 선수만 보고 라인업을 편성한다.

### 실제 코드 근거
- `app/screen/playerScheduleScreen.js`
- `backend/main.py` 의 `/api/schedule/attendance`
- `app/screen/directorScheduleScreen.js`
- `app/screen/lineupScreen.js`

### 발표 포인트
1. 선수는 경기별 참석 상태를 캘린더에서 표시
2. 백엔드는 `home_member`, `away_member` JSON을 갱신
3. 감독 화면은 내 팀 경기만 강조
4. 라인업 화면은 참석 가능한 선수만 후보로 표시

### 기술 발표에서의 힘
- 문제 설명이 쉽다.
- 화면 데모가 바로 된다.
- 데이터 구조와 비즈니스 로직을 둘 다 설명할 수 있다.

### 점수
- 핵심성: `10/10`
- 데모 적합성: `10/10`

## 3-3. 라인업 편성 로직 (`10/10`)
### 왜 가장 강한가
이 프로젝트에서 가장 “기술 발표답게” 말할 수 있는 부분이다.

단순 저장이 아니라 아래 규칙이 들어간다.

- 포지션 중복 방지
- 수비 배치와 타순 배치 분리
- 수비에서 빠진 선수는 타순에서도 정리
- DH 존재 시 투수 타격 제한
- 참석하지 않은 선수는 후보에서 제외
- 배정되지 않은 선수는 후보 일괄 등록

### 실제 코드 근거
- `app/screen/lineupScreen.js`
- `app/constants/scheduleConstants.js`

### 발표 구조 제안
#### 1) 문제
감독은 참석 가능한 선수 중에서 포지션과 타순을 동시에 맞춰야 한다.

#### 2) 데이터 구조
```js
{
  defense: {
    P: null,
    C: null,
    "1B": null,
    ...
    DH: null,
    BENCH: []
  },
  batting: [null, null, ..., null]
}
```

#### 3) 규칙
- 선수 1명이 여러 포지션에 동시에 들어가면 안 됨
- 타순은 수비 포지션에 배치된 선수 위주
- DH가 있으면 투수는 타격 제외

#### 4) 저장 방식
- 홈/원정에 따라 `home_lineup`, `away_lineup` 분리 저장

### 보여주면 좋은 코드
- `assignMember`
- `handleAutoBench`
- 저장 시 `POST /api/schedule/{date}/lineup?side=...`

### 예상 질문
- 왜 lineup을 별도 테이블이 아니라 JSON으로 저장했는가?
- 타순과 수비를 분리한 이유는?
- 나중에 교체/중도 변경까지 지원하려면 어떻게 바꿔야 하나?

### 발표 적합도
- 교수 질문 유발성: `10/10`
- 구현 난이도 설명 가능성: `10/10`

## 3-4. 데이터 모델링 이야기 (`9/10`)
### 말할 포인트
현재 프로젝트는 테이블이 대략 다음 역할로 나뉜다.

- `member`: 사용자 / 선수 정보
- `team`: 팀 정보 / `best_member`
- `schedule`: 경기 일정 / 참석 정보 / 라인업
- `game`: 실제 경기 기록
- `review`: 최근 경기 기반 리뷰

### 여기서 중요한 질문
#### 질문 1
왜 참석 여부를 별도 `attendance` 테이블이 아니라 `schedule.home_member`, `schedule.away_member` JSON 으로 관리했는가?

#### 질문 2
왜 라인업도 별도 row가 아니라 `home_lineup`, `away_lineup` 으로 관리했는가?

### 이 질문이 좋은 이유
이건 **MVP의 속도 vs 정규화된 설계**의 trade-off 를 설명하게 만든다.

### 추천 답변 구조
- MVP 단계에서는 조회/저장 단순성이 중요했다.
- 화면에서 바로 읽고 그리기 쉬웠다.
- 다만 운영형 구조라면 attendance/lineup을 별도 테이블로 정규화할 수 있다.

### 점수
- 기술 깊이: `9/10`
- 설계 토론 유도: `10/10`

## 3-5. 앱 직접 Supabase + FastAPI 혼합 구조 (`10/10`)
### 왜 발표 가치가 큰가
이건 “잘한 점”만이 아니라 “왜 이런 구조가 나왔고, 다음엔 어떻게 바꿀지”까지 말하게 만든다.

### 현재 구조
- 앱 → Supabase 직접
  - 로그인
  - 역할 조회
  - 일부 멤버/팀 조회
- 앱 → FastAPI → Supabase
  - 일정 CRUD
  - 출석 수정
  - 라인업 저장
  - 리뷰
  - AI 카드

### 장점
- 초기 구현 속도가 빠르다.
- 프론트에서 빠르게 화면 개발이 가능하다.

### 단점
- 인증/권한 로직이 한 곳에 모이지 않는다.
- 운영 시 CORS, 감사 로그, 정책 일관성이 약하다.
- API와 DB 접근 경로가 분산된다.

### 발표 포인트
이걸 숨기지 말고, 오히려 이렇게 말하는 편이 좋다.

> “초기 MVP 단계에서는 개발 속도를 위해 혼합 구조를 택했지만,
> 운영 단계에서는 백엔드 일원화 또는 공식 Auth 체계 정리가 필요하다고 판단했다.”

### 점수
- 기술 성찰도: `10/10`
- 질문 대응력 강화: `10/10`

## 3-6. AI 리뷰 + PR 카드 생성 파이프라인 (`9/10`)
### 왜 강한가
이 기능은 핵심 문제 해결과의 직접 연결성은 다소 낮지만, **발표 임팩트는 매우 높다.**

### 실제 흐름
1. `game` 데이터로 최근 경기와 이전 경기 비교
2. `review` 생성
3. 리뷰/아바타 기반 프롬프트 생성
4. Gemini/Imagen으로 이미지 생성
5. Pillow로 카드 레이아웃 합성
6. 갤러리 저장

### 실제 코드 근거
- `app/screen/playerDetailScreen.js`
- `backend/main.py`
- `backend/review_logic.py`
- `backend/review/service.py`

### 발표 포인트
- “AI를 왜 썼는가” 보다는
- “경기 데이터 → 해석 → 시각적 콘텐츠” 로 이어지는 파이프라인을 설명하는 편이 좋다.

### 꼭 조심할 점
이 기능을 **핵심 기능보다 먼저** 꺼내면 프로젝트 초점이 흐려진다.

### 추천 위치
- 본론 70% 끝난 뒤
- “확장 기능 / 차별화 요소” 로 소개

### 점수
- 시연 임팩트: `10/10`
- 문제 직접성: `6/10`
- 확장성: `9/10`

## 3-7. 리뷰 생성 로직 자체를 따로 설명하는 것도 좋다 (`8/10`)
### 핵심 아이디어
최근 경기의 지표와 직전 몇 경기 평균을 비교해서, 선수 상태를 리뷰 문장으로 만든다.

### 발표 포인트
- 타자 / 투수 분기
- 최근 경기 vs baseline
- 이슈 탐지 규칙
- 결과 저장 및 재사용

### 질문 유도 포인트
- 왜 LLM 전체 생성형 방식이 아니라 규칙 기반 리뷰도 같이 썼는가?
- false positive/false negative 를 어떻게 줄일 것인가?

이 주제는 AI 카드보다는 덜 화려하지만, **기술적으로는 더 설득력 있다.**

## 3-8. 브랜치 전략 변화도 기술 발표 소재가 된다 (`8/10`)
### 왜 좋은가
이건 코딩 실력만이 아니라 **협업 구조를 개선해 간 과정**을 보여준다.

### 실제 흐름
- 초반: `main` 기반 작업
- 후반: `dev` 기반 브랜치 전략으로 전환
- 개인 브랜치에 `dev` 머지 후 conflict 해결
- `dev` 로 squash and merge

### 발표 포인트
- 처음에는 Git 숙련도가 낮아서 conflict 해결이 스크럼 마스터에게 몰렸다.
- 후반에는 브랜치 전략을 바꿔 merge 부담을 줄였다.
- 즉, 프로젝트 중간에 **프로세스 자체를 개선**했다.

### 이 주제의 가치
교수/청중에게 “팀이 실제로 협업 문제를 겪고 개선했다”는 점을 보여준다.

## 6. 기술 발표에서 하지 않는 편이 좋은 과장

현재 저장소 코드 기준으로는 직접 확인되지 않는다.

“CSV 업로드가 앱 화면까지 완성됐다.”

### 이유
현재 저장소 기준으로는 백엔드 `/upload-csv` endpoint 는 있으나, 앱 화면 연결은 직접 확인되지 않는다.

“배포까지 끝났다.”

### 이유
현재는 로컬 IP, 환경변수, import 케이스, Windows 폰트 경로 등 운영 전 정리가 필요한 상태다.

## 7. 최종 추천

### 메인으로 가져갈 기술 발표 4개
1. **역할 기반 사용자 흐름**
2. **참석 관리 → 라인업 편성**
3. **라인업 규칙 로직**
4. **혼합 구조에 대한 기술적 회고**

### 서브로 붙일 기술 발표 2개
5. **AI 리뷰 / PR 카드 파이프라인**
6. **브랜치 전략 개선 과정**

### 내 추천 우선순위 점수
- 라인업 로직: `10/10`
- 핵심 사용자 흐름: `10/10`
- 혼합 아키텍처 회고: `9/10`
- 역할 기반 네비게이션: `9/10`
- AI PR 카드: `8/10`
- 브랜치 전략: `8/10`

핵심 한 줄:
> 이 프로젝트는 단순 일정 앱이 아니라,
> **참석 상태를 운영 가능한 데이터로 바꾸고,
> 그 데이터를 감독의 라인업 의사결정으로 연결한 구조**를 보여주는 발표가 가장 강하다.
